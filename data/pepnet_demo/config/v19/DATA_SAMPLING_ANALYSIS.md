| ---------- | --------------- | --------------- | ------- |

## 关键发现

### 1. home CTR 异常高

- v3 home CTR = 3.0%（邻接点击采样）
- v1 home CTR = 36.9%（采样逻辑不同）

**可能原因**：

- v1 也使用了邻接点击采样，但采样窗口不同
- v1 只保留了有点击的样本
- v1 有特殊的正样本过采样

### 2. 各场景 CTR 一致性

- bijia CTR 在 v3 和 v1 中基本一致（~36%）
- haojia CTR 在 v3 和 v1 中基本一致（~13%）
- trend CTR 在 v3 和 v1 中基本一致（~50%）

**这说明**：bijia/haojia/trend 的采样逻辑在 v3 和 v1 中是一致的，但 home 的采样逻辑不同。

### 3. 采样逻辑推测

根据数据特征，推测各场景的采样逻辑：

| 场景   | v3 采样逻辑                   | v1 采样逻辑         | CTR 一致性 |
| ------ | ----------------------------- | ------------------- | ---------- |
| home   | 邻接点击采样（click_cnt > 0） | ?                   | ❌ 不一致  |
| bijia  | INNER JOIN 有点击 request     | 可能也是 INNER JOIN | ✓ 一致     |
| haojia | INNER JOIN 有点击 request     | 可能也是 INNER JOIN | ✓ 一致     |
| trend  | 直接透传                      | 直接透传            | ✓ 一致     |

## 需要确认的问题

1. **v1 home 场景的采样逻辑是什么？**

   - 是否也用了 `click_cnt > 0`？
   - 如果是，为什么 CTR 从 3% 变成了 37%？

1. **v1 表的源表是什么？**

   - 是从 v3 label table 构建的？
   - 还是从原始日志表构建的？

1. **各场景采样逻辑是否一致？**

   - 如果不一致，模型可能学到采样偏差

## 建议

### 方案 A：使用 v3 数据训练（推荐）

如果 v3 的采样逻辑更合理（home CTR = 3% 更接近真实情况），可以考虑：

- 使用 v3 label table 作为训练数据
- 复用 v3 的采样逻辑构建 v19 的数据准备脚本

### 方案 B：继续使用 v1 数据

如果 v1 数据是有意采样的（比如为了提高正样本比例），需要：

- 确认采样逻辑的合理性
- 在评估时使用与训练一致的分层
- 注意 CTR 校准问题（预测概率可能需要 Platt 校准）

### 方案 C：统一采样逻辑

重新构建数据，确保各场景使用一致的采样逻辑：

- home: 邻接点击采样
- bijia: INNER JOIN 有点击 request
- haojia: INNER JOIN 有点击 request
- trend: 直接透传
