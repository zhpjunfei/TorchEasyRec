# 对抗性审核：trend_click → trend_cvr 塔替换方案

**审核日期**: 2026-10-22
**审核对象**: `TREND_CVR_SWAP_PLAN.md`
**审核结论**: ⚠️ **方案有致命缺陷，需修正后才能执行**

______________________________________________________________________

## 一、核心假设验证（致命问题）

### 1.1 假设1: "trend点击率 ~100%" ❌ **错误**

**方案原文**:

> trend场景为查价弹窗，点击率~100%（真实业务形态），is_trend_click作监督信号信息量≈0

**实际数据**（来自之前验证SQL）:

```
| scene | pv       | clicks   | ctr   |
|-------|----------|----------|-------|
| trend | 12,039,226 | 5,802,893 | 50.68% |
```

**问题**:

- trend CTR = **50.68%**，不是~100%
- 50%正样本率的任务**有信息量**，不是常数任务
- 梯度不会消失，只是比bijia(35%)和haojia(13%)更高

### 1.2 假设2: "28.8%正样本率" ⚠️ **需验证**

**方案原文**:

> trend数据中唯一有信息量的标签是转化（28.8%正，每步~65正/160负）

**验证需求**:

- 需要运行SQL确认`is_trend_conversion`的实际正样本率
- 之前SQL5显示trend conv rate = 17.23%（不是28.8%）
- 数据来源可能不同（dt='20261019' vs dt='20261020'）

**正确计算**:

```
从之前SQL5:
- trend pv: 11,450,974
- trend convs: 1,972,750
- trend conv rate: 17.23%

每步4096样本，trend占比9.47%:
- trend样本数: 4096 × 9.47% ≈ 388
- 正样本数: 388 × 17.23% ≈ 67
- 负样本数: 388 - 67 ≈ 321

方案说的"65正/160负"可能是按不同假设计算
```

### 1.3 假设3: "trend GAUC 0.639最低是因为click标签信息量不足" ❌ **更可能是数据质量问题**

**方案归因**:

> trend场景GAUC垫底——与"trend数据带标签噪声"的判断完全一致

**实际根因**（已验证）:

- **37%样本重复**（同一item, request出现2-4行）
- **98.5%重复组合存在标签矛盾**（同时有click=0和click=1）
- 这是**数据管道bug**，不是标签选择问题

**关键洞察**:

- 即使换成cvr标签，如果数据重复问题不修复，同样的问题会出现在cvr任务上
- cvr标签也可能存在曝光/转化拆分导致的重复
- **必须先修复数据质量问题，再考虑任务替换**

## 二、方案逻辑漏洞

### 2.1 "唯一变量 = 监督label"原则被违反

**方案声明**:

> 设计原则: 唯一变量 = 监督 label。权重、掩码、塔结构、样本全部不动。

**实际情况**:

1. **标签分布变了**：click 50.68% → conversion 17.23%（假设验证后）
1. **任务难度变了**：高正样本率任务 → 低正样本率任务
1. **梯度 scale 变了**：BCE loss对不同正负比的优化动力学不同
1. **特征需求变了**：点击预测 vs 转化预测可能需要不同特征

**这不是"唯一变量"，是多个变量同时变化**。

### 2.2 忽略数据修复优先级

**方案未提及**:

- trend数据重复问题（37%重复率）
- 标签矛盾问题（98.5%矛盾率）
- 这些问题的修复优先级**远高于**任务替换

**正确顺序应该是**:

1. 修复数据重复问题（已做）
1. 重新生成样本表
1. 验证数据质量（重复率\<1%）
1. 训练baseline（修复后的数据）
1. **再考虑**是否需要替换任务

### 2.3 缺少回滚后的对比实验设计

**方案缺失**:

- 没有设计"修复数据前后"的对比实验
- 没有设计"click vs conversion"的消融实验
- 无法区分GAUC提升是来自数据修复还是任务替换

## 三、潜在风险分析

### 3.1 任务替换风险

| 风险            | 概率 | 影响 | 说明                                        |
| --------------- | ---- | ---- | ------------------------------------------- |
| CVR正样本过稀疏 | 中   | 高   | 如果实际conv rate只有5-10%，任务可能学不到  |
| 梯度冲突加剧    | 中   | 中   | click和conversion的重复模式可能不同         |
| home CTR退化    | 低   | 高   | 如果trend_cvr学到错误模式，可能污染共享主干 |

### 3.2 数据质量问题未解决

**如果先执行任务替换，不修复数据**:

- trend_cvr同样会面临37%重复率
- 标签矛盾会从click转移到conversion
- GAUC可能不会提升，甚至下降

## 四、修正建议

### 4.1 必须修正的假设

**修正1: trend CTR不是~100%**

```
实际: 50.68%
影响: click标签有信息量，不是常数任务
建议: 保留trend_click任务，或作为对照实验
```

**修正2: 先修复数据，再考虑任务替换**

```
当前状态: 数据已修复（GROUP BY已改）
下一步: 重新生成样本，验证重复率<1%
然后: 训练baseline，观察trend GAUC是否提升至>0.70
最后: 如果仍低，再考虑任务替换
```

**修正3: 验证conversion正样本率**

```
需要运行SQL确认:
SELECT SUM(is_trend_conversion) * 100.0 / COUNT(1)
FROM ... WHERE dt='20261020' AND is_trend_scene=1

预期: 10-20%（基于之前17.23%）
如果<5%: 任务可能过稀疏，需谨慎
```

### 4.2 建议的实验设计

**Phase 1: 数据修复验证**（当前应该做）

```
实验1a: 修复前数据 + 原config（baseline）
实验1b: 修复后数据 + 原config
预期: trend GAUC从0.639提升至>0.70
```

**Phase 2: 任务替换验证**（Phase 1成功后再做）

```
实验2a: 修复后数据 + trend_click（对照）
实验2b: 修复后数据 + trend_cvr（实验）
预期: 如果2b的home CTR GAUC > 2a，则任务替换有效
```

**关键**: 这两个phase必须分开，不能混在一起。

### 4.3 方案修改建议

**如果坚持要执行任务替换**，需要修改方案：

1. **添加前提条件**:

   - 数据修复已验证（重复率\<1%）
   - conversion正样本率已验证（>10%）
   - Phase 1 baseline已训练完成

1. **添加对照实验**:

   - 必须同时训练trend_click和trend_cvr两个版本
   - 对比home CTR GAUC差异

1. **修改成功标准**:

   - 不是只看trend GAUC
   - 必须看home CTR GAUC是否提升
   - 设置回退标准（如果home CTR下降则立即回滚）

## 五、最终建议

### 5.1 当前优先级

| 优先级 | 任务           | 理由                            |
| ------ | -------------- | ------------------------------- |
| **P0** | 重新生成样本表 | 数据已修复，必须用新样本训练    |
| **P0** | 运行验证SQL    | 确认重复率\<1%                  |
| **P1** | 训练baseline   | 观察数据修复效果                |
| **P2** | 考虑任务替换   | 仅在baseline GAUC仍\<0.70时考虑 |

### 5.2 方案决策

**不建议立即执行trend_click → trend_cvr替换**，原因：

1. 核心假设（trend CTR~100%）错误
1. 数据质量问题未验证修复效果
1. 缺少对照实验设计
1. 可能引入新的风险

**建议先执行**:

1. 用修复后的数据训练baseline
1. 观察trend GAUC是否自然提升至>0.70
1. 如果提升至0.70+，说明数据修复是关键，无需任务替换
1. 如果仍低于0.70，再考虑任务替换并设计严格对照实验
